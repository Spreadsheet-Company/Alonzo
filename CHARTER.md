# ALONZO - the browser's Lisp machine

*The charter of a repository beside Frazaro, named for Church, whose calculus became the language of the machines rather than a foundation for arithmetic (`Frazaro/docs/HORIZON.md` §1). Alonzo is VLA all the way down to the host's draw call: a game engine in WebAssembly whose language is VLA, in a crate of its own, whose scene is VLA's grid, whose devices are sheets, and whose first game is Frazaro, the spreadsheet. Written 2026-10-08 at the owner's call, from the sitting of the previous session, and revised the same day after the owner's two sittings on the boundary between the three (§4).*

*What this document is not. It is not a Frazaro roadmap line: nothing here is an item there, it mints no ID in `Frazaro/docs/ID_REGISTRY.md` and takes none, and Frazaro's language crate, core crate, command-line door, add-in and treaty never depend on it (rule 1). It is not a commitment to a date. This repository governs itself. While it forms, this file is a living document, rewritten in place at the owner's call (the owner's decision of 2026-10-08); when the owner freezes it, the house rules `HORIZON.md` states for every ledger in `docs/` take over, append-only, a correction added and dated, never written over. Where this file and the code disagree, the code is right. Marks follow `HORIZON.md` for ideas and for arguments about the present, and `docs/PROTOCOL.md` for figures: every idea is* **math exists** *(the result is published and the only work is building it in),* **engineering** *(nothing new has to be true, but someone has to build it) or* **fiction** *(it needs the world to change, usually socially); an argument about the present is* **exhibit** *(a dated, public, checkable fact, its source in §10),* **shelf** *(a claim a file in the Frazaro repository already makes, cited) or* **recommendation** *(the sitting's advice, the owner's to take or leave); every figure is a* **measurement**, *dated, with its method, a* **prediction** *written before the measurement that tests it, or* **derived**, *arithmetic over stated inputs. An idea with no mark is a vibe, and this file does not keep vibes. Frazaro's standing decisions that cross the road are named where they bind: `SD-13` (no outbound network call, ever, without a dedicated re-litigation of this decision), the owner's veto of `GENSYM`, `SD-18` (VBA stays the reference for the language) and the conformance treaty.*

## 1. The thesis

A Lisp machine was a computer whose language went all the way down: the machine understood the language's data, and the microcode was written to it. Alonzo is that idea in the one machine everyone already has, the browser, with the honesty the browser imposes (§2). The language is VLA, the Lisp Frazaro is written in, held to one meaning by two implementations and a treaty (*shelf*: `Frazaro/conformance/README.md`), and by the owner's decision of 2026-10-08 cut into a crate of its own, `vla-lang`, that Alonzo and Frazaro consume alike (§4, rule 1). Three things, then, with three names: VLA is the machine, a Lisp whose heap is a grid; Frazaro is the set of bridges into and out of it, from human languages to VLA with a proof per sentence, and from VLA to the spreadsheet hosts and back; Alonzo is the devices and the clock. The scene is a sheet of cells, since the spreadsheet is the only mass-market two-dimensional medium humans have (*shelf*: `HORIZON.md` §3, Peirce's sheet of assertion). The engine is a WebAssembly module that has the sheet evaluated and draws it, frame after frame. The first game on it is Frazaro: a spreadsheet, which is a member of class game (§3), and the one game the project already knows how to score, since its oracles exist (*shelf*: `conformance/README.md`, oracles 7, 8 and 11, the build, reflect and view goldens). The thesis in one line: a spreadsheet is a game whose frame rate is one, and an engine that can draw sixty can draw one. (*engineering*)

## 2. The honest bottom

A WebAssembly module sees only its own linear memory, with the functions, tables and globals it defines, and the imports its host chose to give it. Nothing else exists to it; it cannot open a file, draw a pixel or hear a key except through a function the host handed in at instantiation (*exhibit*: the WebAssembly specification's module, import and instantiation sections, and its embedding appendix). Frazaro's core takes that to its limit: its module is compiled with an empty import section, so that `SD-13` is a fact verified on the artifact rather than a promise, and `tools/check_core_imports.ps1` pins the count at zero in the CI job that builds the artifact, on every push to `main` and every pull request (*shelf*; *measurement*, 2026-10-08: the check over the release wasm built 2026-10-07, 988,338 bytes, 0 imports). Alonzo's module will have imports, because a game must draw, sound and listen, and every one of those is the host's function: the canvas, with its 2D context today and WebGPU where it is needed; the Web Audio graph; the input events. Its twin of that check is an allowlist (*recommendation*, written with the first brick): a check that names every import the module takes, the canvas, the audio graph, the input events, the animation frame, the file picker, and fails on any other, `fetch` first among them. `vla-lang`, cut from Frazaro's core, keeps the empty import section, since the language adds nothing that needs one. So the stack stops there. Below the draw call sit the browser's compositor, the GPU driver, the window system and the firmware, none of which Alonzo writes, as Linux stops at the firmware it did not write and the keyboard controller it cannot see. "All the way down" means down to the draw call, and the draw call is rented. The rent is the honest bottom of the thesis, and §4's third rule is what keeps the project from pretending otherwise. (*engineering*)

## 3. A spreadsheet is a member of class game

A sheet of coloured cells is a framebuffer. A cell that is a formula of its neighbours is a fragment shader: a pure function of the cells around it, run once per frame for every cell. A recalculation is a frame. `HORIZON.md` §2 already reads the sheet as one enormous `letrec` (*shelf*), and the view record of `KERNEL.4` is one window of that framebuffer, printed as lines a viewport draws from (*shelf*: `Frazaro/cli/README.md`, `frazaro view`; the treaty's oracle 11). What is new here is only the frame rate (*engineering*: the reading is free, the frame loop is the work). One caution, *derived* from §7's own figures: the view record is lines of text, printed at some twenty-five thousand lines a second on the day of writing with the stopwatch's overhead included, and a frame of 64,000 cells thirty times a second is seventy-eight times that; so the record is the oracle, and the frame path is a typed array of colour indices read out of the Screen sheet, held equal to the record by a test (*recommendation*).

The numbers, *derived*: a screen of 320 by 200 is 64,000 cells; at 30 frames a second that is 1,920,000 cell evaluations a second, about two million, which is a fantasy console's budget: TIC-80 draws 240 by 136 at 60 frames a second, 1,958,400 pixels a second, within two percent of the line, and PICO-8 128 by 128 at 30, a quarter of it (*exhibits*; *derived*); that budget, in WebAssembly, is what Alonzo would be. A screen of 1920 by 1080 is 2,073,600 cells; at 60 frames a second that is 124,416,000 cell evaluations a second, about 120 million, which is a GPU's job and (*prediction*) not Alonzo's first decade. The engine's first measure is therefore cells evaluated per second (§7), and the two-million line is the floor it must clear to be a console at all. Whether a recalculation engine built for `KERNEL.7`'s subset can be driven at thirty frames is *engineering*: topological evaluation over a dependency graph is published ground (*math exists*: Sestoft 2014), and the sheet-as-shader reading adds only the frame loop.

## 4. The five rules, and the frame

They keep Alonzo from becoming the Lisp machine, which is the thing that lost. The first two were rewritten on 2026-10-08, when the owner set the condition that Alonzo be a self-contained substrate for the games after Frazaro and that Frazaro own nothing such a game needs; the fourth was added the same day, the fifth at the scoping of the first commit, the owner adopting it as `AD-5`, and the frame beneath them is the engine's contract.

1. **VLA's seams are the interface, and Frazaro is a door.** Three crates, in one dependency order. `vla-lang` is the language and nothing else: the reader, the expander, the forms and the head table, the grid (the sheet model with its A1 coordinates), evaluation over the grid (recalculation's mechanism when `KERNEL.7` lands, with a registry seam for functions; the interpreter when `PORT.10` lands), the view record as the grid's projection, and in time the VLA-to-WebAssembly emitter; it has no clock, no English and an empty import section. `frazaro-core` consumes it and holds the bridges: the phrasebooks and the matcher with a proof per sentence, Excel's function library registered into VLA's evaluator, the VBA and formula emitters, the OOXML and OpenDocument writer and readers, the stamp, and the treaty's oracles. `alonzo` consumes `vla-lang` and never `frazaro-core`: a game's dependency tree holds the language crate and the engine crate and not the Frazaro core, which is the owner's condition stated as a check (*recommendation*: `cargo tree` in every game's CI). A game written in English is translated by Frazaro at build time and ships as VLA, so Frazaro is to a game what a compiler is to a binary. Frazaro's language crate, core crate, command-line door, add-in and treaty never depend on Alonzo; Frazaro's web door does, from the day its grid is Alonzo's viewport (rule 2), as a game depends on its engine. The cut of `vla-lang` from `frazaro-core` is Frazaro's work, before `KERNEL.7`; on the day of the decision it is about 4,300 of the core's 30,559 lines (*measurement*, 2026-10-08, `wc -l` over `core/src` with each file assigned by what it references). Until Alonzo passes the treaty's oracles for what it renders, the arrow points one way.
2. **Every early brick is also a Frazaro item, laid where it is first needed.** The sequencing stands: the recalculation engine (`KERNEL.7`, the declared subset's floor, and `KERNEL.20`, speed measured); the canvas renderer of the view record (`KERNEL.5`, the viewport); a VLA-to-WebAssembly emitter as the third backend beside VBA and the interpreter, the substrate `PORT.10` wants when the first gear's directives run in memory at the speed a frame needs (*shelf*: `BETA_ROADMAP.md`'s entries for `KERNEL.7`, `KERNEL.20` and `KERNEL.5`; the emitter has no entry yet, `PORT.10` being the interpreter over the sheet model and `HORIZON.md` §12.2 listing the core's emit targets as VBA, formulas and JavaScript, so the emitter is the sitting's *recommendation* until an item mints it); and only then the frame loop, sprites and input, which are Alonzo's alone. What the revision changed is where the code lands. An item's ID is Frazaro's and stays in Frazaro's registers; its code lands on the side of the line rule 4 draws: the evaluator in `vla-lang`, the viewport in this repository as the Screen device over the view record, with Frazaro's web page consuming it and staying the translate page it is until then. The item boundary and the code boundary are two boundaries, and the roadmap entry of an item laid here says so in one line. A brick that no Frazaro item needs is not laid until those are.
3. **Nothing Frazaro rents is rebuilt until Frazaro has users on the rented version.** The rasterizer (the canvas's own text and paths), the shaping engine (the browser's: HarfBuzz in Chromium and Firefox, Core Text in Safari; *exhibit*) and the font files stay on the rented list until a measurement says the rent is the bottleneck, and the measurement is named before the rebuild begins. The Lisp machine rebuilt the whole stack from the processor up; Emacs owns its buffer and its redisplay, rents the shaping, the drawing and the fonts beneath them, and is still here (§5).

4. **Frazaro has no clock; Alonzo is the clock.** Everything whose output can be a golden is VLA's or Frazaro's: a pure function, or a step function that reports how far it got (`SD-34`). Everything that can only be measured is Alonzo's: the loop and its budget, the draw, the sound, the input, the files, and the state that lives between frames and that no program sees (`SD-23`'s list: selection, scroll, the half-typed edit; a game's camera and its input buffer). The check on each side: `vla-lang` and `frazaro-core` at zero imports, `alonzo` at its allowlist (§2). Excel's volatile functions fall on Alonzo's side of the line: `NOW` is the Clock device and `RAND` is a seeded cell, so determinism holds without a rule.
5. **The engine's imports are the host's functions, named by hand and held to a list; the engine crate depends on the language crate and nothing else.** Each import is an `extern "C"` function the host shim provides, a blit, a note, the input and clock writes, the file read, declared one by one as `frazaro-core` declares its C surface in `abi.rs`, so that §2's allowlist reads the host's names and the shim is read in review rather than generated. No `wasm-bindgen`, no `web-sys`, no crate beside `vla-lang`: generated glue would put dozens of a toolchain's imports into the section the allowlist holds, and a second dependency would put a stranger's code between the language and the draw call. (`AD-5`, adopted by the owner 2026-10-08 at the scoping of `REPO.1`.)

**The frame.** Alonzo is Varvara to VLA's uxn (§5): where Varvara maps its devices into uxn's memory at fixed ports, Alonzo maps its devices into VLA's grid as sheets: Screen, Audio, Input, Clock, File. Each frame, Alonzo writes the input and clock cells, asks VLA to step, reads the Screen sheet and the effect cells, and draws. Every input is a cell Alonzo writes. Every effect is a cell Alonzo reads. The engine's whole contract is four calls into `vla-lang`: load a cartridge, write cells, step, view. The Screen sheet of a cartridge at 320 by 200 is the framebuffer of §3, which is why every cartridge pays §7's second number whatever its own logic costs. A frame is a dependency graph over two buffers: a cell of this frame reads the previous frame anywhere, and this frame's cells wherever the reads are acyclic, so the grid is double-buffered by construction, a self-reference across frames is never a circular reference, and a cycle within a frame is refused by name, as the treaty's recalculation will refuse it. That makes the frame strictly more expressive than a synchronous automaton, where every read is of the last frame (the fragment shader of §3), and than a scan-order one, where every read is of this frame in one fixed order: both are special cases of the graph. The graph's depth is the frame's critical path and its width at each level is the parallelism on offer, which is why the synchronous frame is the most parallel and the scan-order frame the least (*engineering*; Excel has split its own calculation chain into independent subchains across cores on this principle since 2007, *exhibit*). The first parallelism is the cheap one and needs no host: every cell of a cellular rule carries the same formula in R1C1, so a field is one formula shape evaluated once per cell, vectorized, which is `KERNEL.20`'s first and third advantages applied to a game, and the shader's dispatch in the spreadsheet's own terms. Threads come after a measurement, and they are a device, since the host spawns them and must serve the page cross-origin isolated for the shared memory they need (*recommendation*). The loop's own parallelism is pipelining, the draw of one frame beside the step of the next, and it is Alonzo's. The specification is that page, the device sheets' layout and the four calls, written before the first cartridge, in uxn's lesson.

(*recommendation* throughout; the owner's to amend)

## 5. The lineage, each with the lesson it carries

*The entries are exhibits; each lesson is the sitting's reading of its exhibit (*recommendation* throughout).*

- **Symbolics and the Lisp machines** (1980 to the Chapter 11 filing of January 1993). Lisp to the microcode, Genera, the Ivory chip; lost on cost, when commodity workstations riding Moore's law undercut a machine whose every layer was bespoke, and the AI winter took the buyers (*exhibit*). *Lesson:* owning the whole stack is a rent the market charges every year; rent whatever gets cheaper faster than you could build it.
- **Project Oberon** (Wirth and Gutknecht, 1986 to 1989; the book 1992; the FPGA edition 2013, with the processor too). A whole stack small enough for one person to know and implement, the project's own claim: compiler, operating system and in the end the hardware; built by two, the 2013 processor Wirth's alone; influence, not users (*exhibit*). *Lesson:* a whole stack small enough for one person to know is possible and teaches, and it does not by itself gather users; Alonzo's stack must gather them as a game does, by being played.
- **Emacs, with `ses.el` and `org-table`.** The most successful Lisp environment there has been, by the measure of still shipping since 1985 (the judgment is the sitting's, the dates are *exhibits*); a spreadsheet in Lisp (`ses.el`, Yavner, in Emacs since version 22) and another inside `org-mode`'s tables; it has drawn its text through FreeType since 23.1 (2009), and since 27.1 (2020) it shapes it through HarfBuzz and, when built with Cairo, draws it through Cairo, and nobody minds (*exhibits*). *Lesson:* rent text, own the buffer; a Lisp environment is judged by what its buffer can do, never by whose glyphs it draws.
- **Smalltalk and Squeak** (1996; Ingalls, Kaehler, Maloney, Wallace and Kay, "Back to the Future", 1997). The image; a virtual machine written in Smalltalk itself and translated to C; BitBlt its own (*exhibit*). *Lesson:* a system written in itself, owning its pixels, can live for thirty years on a community; its rent, the host's window and operating system, was never the problem.
- **uxn and Varvara** (Hundred Rabbits, 2021). A machine of 64 KB of addressable memory with a short specification, under MIT, and emulators written for love on hardware the authors never saw, the project's own list and others' (*exhibits*). *Lesson:* a small, finished specification gathers ports; the specification is the product. Alonzo's specification is §4's page, the device sheets and the four calls, over a view record and an ABI that are already written down (*shelf*: `conformance/README.md`, oracle 11; `core/src/abi.rs`).
- **PICO-8** (2015; 128 by 128, 16 colours, 30 frames a second by default, 60 on request; commercial and closed) **and TIC-80** (240 by 136, 16 colours, 60 frames a second; MIT). The fantasy console: limits as a feature, a cartridge as the unit, and a community that fills each console's own forum with them (*exhibits*). *Lesson:* a finished console with stated limits gathers games; Alonzo's limits are a sheet's, and they are to be stated, not discovered.
- **GOAL and OpenGOAL.** Naughty Dog's Lisp, in which over 98 percent of the Jak trilogy was written, the project's own figure; and OpenGOAL (2020 onward), a community that rewrote the compiler from nothing, decompiled the games and has ported Jak 1 and Jak 2 to PC under the ISC licence, with Jak 3 under way, for the challenge of it (*exhibits*). *Lesson:* a Lisp game engine has shipped, and hackers will optimize one for love; this is the precedent §6's hypothesis stands on.
- **Figma, Flutter Web, Google Docs and Sheets on canvas.** Figma's editor is C++ compiled to WebAssembly, drawing its canvas with WebGL and, since 2025, WebGPU; Flutter's web renderer CanvasKit is Skia compiled to WebAssembly; Google Docs moved its document surface to canvas in 2021, saying its assistive-technology support was unaffected, which it kept by a side DOM; Google Sheets draws its grid on canvas, a fact the sitting could source only at second hand (*exhibits*, §10). *Lesson:* own the document surface, rent text and chrome; and the accessibility Docs pays for with a side DOM, Frazaro pays for with `SD-35`, the program is the accessible workbook, which costs no second tree, since the sentences already say everything the grid shows (*recommendation*).

## 6. The social hypothesis, stated so it can fail

*The hypothesis.* Hackers who will not touch a spreadsheet will optimize a game engine, and a spreadsheet that is a game on that engine inherits the speed. Why it might be true: §5's OpenGOAL, and every fantasy console's community. Why it might be false: the people who optimize an engine optimize what a game touches, and a spreadsheet's speed lives in recalculation, which a frame loop never touches unless the recalculation engine *is* the frame, which §3 makes so by construction and which a game will only exercise if the game's logic is cells. So the hypothesis has a hidden premise, that a game's logic is written as cells and not as a script beside them. Rule 1 makes the premise structural, since Alonzo holds no evaluator and no parser and a game's logic has nowhere else to live, and the game is designed to that premise. (*fiction*, social, until tested)

*The test* (*recommendation*). Ship a fantasy-console-sized VLA game on a cell sheet, 320 by 200 or smaller at 30 frames a second, whose logic is formulas of neighbouring cells, and count forks and pull requests on this repository and on `vla-lang`'s over one quarter from the release of the first game repository (the sand toy, below; the engine's own release, with Life aboard, gets its count written beside it and is not the test), since an optimization of the evaluator lands in the language crate and one of the loop, the renderer or the devices lands here, and the hypothesis is about both.

*The games, in order* (*recommendation*, 2026-10-08, in the order the owner proposed the same day; each makes the next cheap, the instrument before the operation). First, Conway's Life at 320 by 200: the engine's own cartridge, shipped in this repository as the fixture §7's floor is measured on, and the first thing played on the engine, since the spreadsheet becomes it by raising one number, the frame rate, on a sheet whose every cell is the same formula of its eight neighbours; it needs the Screen and Clock devices and the declared subset's first functions, and nothing else; at depth one it is the throughput and parallelism benchmark, and it cannot test the graph. Second, and the first game repository, a falling-sand toy: the one genre whose entire logic is a per-cell neighbour rule and that is played, the mouse painting materials into the grid; it adds the Mouse device, a palette table and the intra-frame graph at depth 200, so it is the test of the grid's real machinery, and it is the game the hypothesis is counted on, so the quarter of the prediction below runs from its release. It is the sitting's pick for the game for three reasons. It can fail §3's floor with the graph in play, since every one of its 64,000 cells works every frame through a chain two hundred deep, where a game in Tetris's shape touches a few hundred cells a frame and cannot fail it, and a test that cannot fail is not a test. Its community, The Powder Toy's, is the population the hypothesis names, people who optimize a cellular automaton for love (*exhibit*). And its supposed wrinkle, that sand slides asynchronously while a frame is synchronous, dissolves on the grid (the owner's question of 2026-10-08, which corrected the first draft of this sentence): a spreadsheet frame is a dependency graph over two buffers, not a synchronous automaton, and the scan order a sand rule wants is a downward chain, each row's cells reading the row beneath them in this frame and the rows above them in the last (§4, the frame), so the rule is written as formulas, with the receiving cell choosing among the grains that could enter it; the Margolus neighbourhood (Toffoli and Margolus 1987) is the workaround of a substrate that can read only the last frame, and the grid is not one (*math exists*, on the shelf, unneeded). Third, a falling-block game in Tetris's shape: the best exercise of the grid's logic, line clears, a shape table, a seeded bag, keys and the Audio device, under its own name and look, since the name and the look are The Tetris Company's (*exhibit*: Tetris Holding v. Xio Interactive, D.N.J. 2012). The arcade pick that can also fail the floor, if one is wanted before that, is a lane-crossing game in Frogger's shape at pixel resolution, every lane cell its neighbour's last value. The order introduces the devices one or two at a time, Screen and Clock, then Mouse, then keys and Audio, and the functions the same way.

*The baseline* (*measurement*, 2026-10-08, the GitHub API): `Spreadsheet-Company/Frazaro`, public since 2026-09-05, has 0 forks and 2 stars, so a count of the size predicted below is a signal and not the noise of a public repository.

*The prediction, written before the release* (*prediction*, 2026-10-08): within one quarter of the release of the game the test names, this repository and `vla-lang`'s together take at least 10 forks and at least 3 pull requests from people who are not the owner, and at least one pull request makes the engine measurably faster on its own benchmark (§7). The hypothesis fails if a quarter passes with fewer than 3 forks or with no pull request from outside. A result between, three to nine forks with an outside pull request, leaves the hypothesis standing and the prediction unmet, and the number is then revised in a dated line. The owner may amend the number by a dated line before the release; after the release, the number stands, and the result is written here beside it, either way.

## 7. The first numbers

The first is `KERNEL.3`'s renderer benchmark (`Frazaro/docs/PROTOCOL.md` §7; *shelf*, uncommitted on the day of writing): two throwaway renderers of a real view record of a 10,000-line program, a virtualized DOM table and a canvas drawn with the 2D context, timed for first paint and scroll frame at a normal window and a full-screen one. It is Alonzo's first number because the renderer of the view record is the first brick rule 2 allows, and because its decision rule (`PROTOCOL.md` §8.1) chooses canvas only if a canvas clears a 16 ms frame and is crisp at the machine's pixel ratio; a canvas that cannot do that for a spreadsheet cannot do it for a game. *Measurement* (the owner, 2026-10-08: Chrome 154 on Windows, a 2560 by 1440 screen at a pixel ratio of 1.5, in fullscreen, a 60 Hz display with a 16.7 ms interval; the record of the 10,000-line program, 20,006 lines, printed by the native debug door in 893 ms and read by the page in 13.5 ms): the synchronous render of a window cost 0.4 to 1.2 ms for either renderer at either window; every scroll step's frame time sat on the display's interval, p50 16.5 to 16.6 ms, p95 16.6 to 16.7, max 16.7 to 16.8, with no frame over one and a half intervals in 480 steps; first paint 16.4 to 16.8 ms. *The reading:* the rule's threshold of 16.7 ms is the display's own interval, so its yes-or-no column reads a tenth of a millisecond of timer jitter, and the page's own robust column, frames over one and a half intervals, says both renderers clear both windows. By the rule's letter only the canvas clears the full-screen window (p95 16.6 against the DOM's 16.7) and step 3 chooses it; by the robust reading both clear and step 2 chooses it; the choice is the same under both, **canvas**, subject to step 2's crispness check by eye at the machine's ratio, which the owner reports separately, and it paints the normal window inside 100 ms (step 5). *Against the prediction:* both clear, as predicted at the normal window and, contrary to the prediction, at the full-screen one too; first paint cannot be under 10 ms by the measure's own definition, since it spans a refresh, and the synchronous render was under 1.2 ms; the DOM's first paint was under 30 ms as predicted. *What it says for Alonzo:* at a spreadsheet's size the renderer costs a tenth of the budget and is not the bottleneck; the game's Screen of 64,000 cells is a different path, a typed array blitted whole (§3), and gets its own number with the Life cartridge. The same table belongs in `PROTOCOL.md` §9.2 and in `CALLOSUM.md`'s slot of 2026-10-08, which are Frazaro's edits.

The second is the recalculation engine's cells evaluated per second when `KERNEL.7` lands, measured on `KERNEL.6`'s fixtures and on the benchmark cartridge, Conway's Life at 320 by 200, every cell a formula of its eight neighbours (*exhibit*: Conway, in Gardner's column of October 1970; its optimization lineage, Gosper's HashLife of 1984 and Golly, is the population §6 names), against §3's floor of two million a second; the honest comparison is to a Life that evaluates every cell every generation, as a shader does, and not to HashLife, which exploits regularity to skip generations and is a different machine. The cartridge lives in this repository, since a floor's fixture lives beside the check that reads it. *Measurement to come.* Until then the only speed figures are Frazaro's door numbers (*measurement*, 2026-10-05, `web/CALLOSUM.md` §10, the native release door): a 10,000-line program translated in 105 ms and built to a workbook in 363 ms; and the view record of that program, 20,006 lines, printed in 812 ms by the native debug door (*measurement*, 2026-10-08, `tools/bench_view.ps1`'s stopwatch around the call, PowerShell's reading of the lines included).

## 8. What is not built, by name, and what Alonzo is not

*(*recommendation* throughout, the sitting's; the owner's to amend by a dated line)*

*Not built, and why.* A rasterizer, a shaping engine and font files (rule 3: rented from the canvas and the browser until a measurement says otherwise). A GPU driver, a window system, an input stack (§2: below the draw call). A network layer: `SD-13` crosses the road, so Alonzo makes no outbound call, ever, without the dedicated re-litigation `SD-13` names, and a multiplayer game is *fiction* here, by file if it is ever anything. A second scripting language: VLA is the language, there is no Lua and no JavaScript inside the engine, brevity and never power, the charter's own rule in the words `HORIZON.md` §12.9 uses of libraries (*shelf* for the phrase alone). An asset pipeline beyond the workbook: a sprite is a range of cells, a palette is a library of `Define` sentences (`SD-32`), a level is a sheet. A physics engine, until a game needs one and names the sentence that needs it (`SD-7`). An editor of its own: the two-pane page is the editor (`KERNEL.14`). A sound synthesizer beyond the Web Audio graph's own nodes. An evaluator or a parser of VLA: Alonzo reads no VLA and computes no cell, every value is `vla-lang`'s, and that is what makes §6's hidden premise structural (rule 1).

*What Alonzo is not.* Not a Frazaro roadmap line, and not a line of items in Frazaro's registers: its early bricks are Frazaro's items (rule 2), and any later item of its own is minted here, under this repository's own governance. Not a dependency of Frazaro's language crate, core crate, command-line door, add-in or treaty, ever, and a dependency of Frazaro's web door only from the day its grid is this repository's viewport (rule 1). Not a product, a company or a brand unless the owner says so; the name is the owner's. Not the Lisp machine: it does not own the hardware, the firmware, the display or the fonts, and the five rules are written so that it never wants to.

## 9. The licence, proposed

*Recommendation; the owner's call.* Apache-2.0, for four reasons. It is the territory of the crate Alonzo consumes (`vla-lang`, cut from `frazaro-core`, keeps the workspace's Apache-2.0; *shelf*: `Frazaro/Cargo.toml`, `REUSE.toml`), and the Delta rule that a licence boundary always falls on a repository or file boundary (*shelf*: `Delta/README.md`, `CUTS.md` §4) is best kept by giving the engine's kind of repository the engine's terms, so that a door that one day embeds Alonzo stays in one territory. It carries a patent grant, which matters for a renderer and an engine that will take optimizations from strangers. It takes DCO inbound and no CLA, as `CUTS.md` decided for Frazaro. And the communities §6 counts on live under permissive terms: TIC-80 and uxn under MIT, OpenGOAL under ISC (*exhibits*, §10), and PICO-8 commercial and closed (*exhibit*: sold at $14.99, no source published) and gathering its games regardless, which says the licence is not what gathers games, the console is. The alternatives, and why not: `MIT OR Apache-2.0`, the Rust ecosystem's convention, if the owner wants the broadest uptake there, at the cost of a second text and a weaker patent story under the MIT half; MPL-2.0 or GPL would make optimizations flow back by law, but the hypothesis is that they flow back for love; a GPL engine could not be embedded in Frazaro's doors, whose own code is Apache-2.0, without conveying the doors under the GPL, and an MPL-2.0 engine could, as a Larger Work, the way the `frazaro` crate already carries the MPL-2.0 `english.vla` beside Apache-2.0 code under `Apache-2.0 AND MPL-2.0`, so MPL-2.0 would buy only file-level flow-back the hypothesis says comes for love. A game written on Alonzo is its author's, as a workbook built by Frazaro is its author's (*shelf*: `OUTPUT-EXCEPTION.md`), and the analogue of that file is written the day the first game ships. The licence file goes in when the owner has chosen; until then this section is the proposal. The crate names are chosen (the owner, 2026-10-08): `alonzo`, free on crates.io that day, and `vla-lang`, since `vla` is held by a yanked crate of 2023 and a published name is not released by yanking (*exhibits*, §10).
